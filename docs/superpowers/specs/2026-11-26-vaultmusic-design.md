# VaultMusic 設計書（2026-11-26 / 方式C: Drive 直再生）

## 0. 改訂履歴

- v1: 暗号化 Vault に音源を複製する方式（A/B）で設計。
- **v2（本版）**: 既存の Google Drive 音楽フォルダをそのまま再生する方式 **C** を採用。packer・暗号化・パスフレーズを廃止。

## 1. 目的と背景

Google Drive にすでに置いてある自分の音楽ライブラリを、iPhone の通学中に Spotify のように聴ける軽量 PWA を作る。

- 音源は Google Drive の既存フォルダに **すでに平文で存在**（約 494 曲 / 3.71GB、mp3 中心）。
- したがって、アップロード・暗号化・変換は行わない。Drive をそのままライブラリとして読む。
- タグは不完全：title 45%、album 42%、albumartist 0%、track 番号 2%。フォルダは 15 個、カバー画像ファイルは 0 枚、埋め込みアートは mp3 の 45%。
- ファイル名は 170 曲が `A - B` 形式、366 曲に日本語を含む。タグの無い曲はファイル名から補完できる。
- そのため「アルバムカバー一覧」中心ではなく、**曲とフォルダ中心**のライブラリにする。
- 主戦場は **iPhone・通学中の画面オフ再生**。画面ロック中の連続再生、ロック画面／イヤホン操作、電波が悪い場所での再生、前回の続きからの再開を最優先する。

## 2. ゴール / 非ゴール / アンチゴール

### ゴール
- 既存の Drive フォルダを指定するだけで、約 500 曲のライブラリが数秒で表示される
- iPhone で画面ロック中も 30 分以上、自動曲送りで連続再生できる
- ロック画面・イヤホン・Bluetooth の再生操作が効く
- 選んだアルバムを端末に保存し、機内モードでも再生できる
- **モバイル通信を既定で使わない**。保存済みの曲は通信ゼロで再生でき、1 時間の通学で 0MB を実現できる
- 未保存の曲を再生するときだけ、サイズを示して通信の許可を求める
- アプリを終了しても「続きから」再開できる
- 既存の VaultStream に一切影響しない

### 非ゴール（MVP）
- 暗号化（E2EE）・パスフレーズ・アップロード・音源変換
- 低ビットレートの派生ファイル生成（データ削減は事前保存で行う）
- 公開共有、複数ユーザー
- 歌詞、EQ、クロスフェード、ギャップレス保証
- 音楽ファイルの編集・タグ付け・削除
- Android 最適化（動くが、検証は iPhone 優先）

### アンチゴール
- 画面ロックで音が止まる
- モバイル通信 OFF なのに、裏でストリーミングやカバー取得が走る
- 曲送りが 5 秒以上かかる／毎回ダウンロード待ちが入る
- ライブラリ表示のたびに Drive を全走査して待たされる
- Drive 上のファイルを変更・削除してしまう

## 3. 前提・制約

- 構成：Next.js（静的 export）＋ Tailwind ＋ Google Drive API v3 ＋ Cloudflare Pages 無料枠。バックエンドなし。
- 認証：ブラウザ内 OAuth（GIS Token Client）。既存 VaultStream の Web クライアント ID を再利用し、VaultMusic のオリジンを「承認済み JavaScript 生成元」に追加する。
- スコープ：既存 VaultStream のクライアントと互換のためフル `drive`。コードは読み取り API しか呼ばない。
- 音源フォルダ：ユーザーが Drive のフォルダ URL またはフォルダ ID を貼って指定する。アプリはそのフォルダ配下だけを読む。
- 音源形式：mp3 / m4a（AAC）。opus は iOS Safari で再生が不安定なため、一覧に表示しつつ「この端末では再生できない可能性」を明示する（MVP では再生対象から除外してもよい）。
- 暗号化しない。音源・ファイル名は Drive 上に今までどおり見える。これは方式 C の受け入れたトレードオフ。
- 個人利用のみ。共有リンクは作らない。ファイルの作成・更新・削除は行わない。
- データ削減が主目的。音源は mp3 のままなので、通信量を減らす手段は「事前保存」であり、ビットレート変換はしない。
- iOS Safari は Wi-Fi とモバイルの判別 API（`navigator.connection`）に対応していない。ネットワーク種別を推測せず、ユーザーの明示スイッチで制御する。

## 4. 方式の選択

| 案 | 内容 | 判断 |
| :--- | :--- | :--- |
| A. 暗号化 Vault に複製 | 元を残したまま暗号化コピーを Drive に置く | 不採用（二重保存、元が見えたまま） |
| B. 暗号化 Vault に移行 | 暗号化して元を削除 | 不採用（パスフレーズ紛失＝全損、実装も大掛かり） |
| C. 既存フォルダを直接再生 | Drive の音楽フォルダをそのまま読む | **採用** |

C の理由：音源はすでに Drive にあり、目的は「通学中に快適に聴くこと」。アップロードも変換も暗号化も不要で、最短で目的を満たせる。Drive API の Range 取得でストリーミングでき、500 曲規模ならライブラリ読み込みも一瞬。E2EE を諦める代わりに、実装・運用・容量の負担を大幅に減らす。

## 5. 全体構成

```
vaultmusic/
  pwa/        Next.js 静的 PWA
  docs/
```

主要モジュール：

- `lib/auth.ts`：GIS Token Client、トークン更新、スコープ管理
- `lib/drive.ts`：フォルダ一覧・再帰列挙、ファイル取得 URL、Range 取得
- `lib/library.ts`：Drive のメタデータから Track / Album を組み立て、IndexedDB にキャッシュ
- `lib/metadata.ts`：`audioMediaMetadata` の補完、ID3 / MP4 タグのフォールバック解析
- `lib/player.ts`：React の外に置くシングルトン再生エンジン
- `lib/offline.ts`：IndexedDB の音源・カバーキャッシュと容量管理
- `lib/mediaSession.ts`：ロック画面・イヤホン操作
- `lib/userData.ts`：プレイリスト・お気に入り・履歴・キュー（ローカル保存）

packer は作らない。

## 6. Drive アクセス

### 6.1 フォルダ指定
- 設定画面でフォルダ URL / ID を受け取り、`files.get` で存在と権限を確認して保存する。
- 初回は Drive のフォルダ URL を貼るだけで完了。パスフレーズ入力はない。

### 6.2 ライブラリ列挙
- 指定フォルダ配下を再帰的に BFS で列挙する。
- 1 リクエストでファイルとサブフォルダの両方を取得する：

```
GET /drive/v3/files
  q: '<folderId>' in parents and trashed = false
  fields: nextPageToken, files(id, name, mimeType, size, modifiedTime, createdTime, parents, audioMediaMetadata, thumbnailLink)
  pageSize: 1000
```

- 対象は `mimeType` が `audio/` で始まるもの、または拡張子が mp3 / m4a / aac / opus のもの。
- 約 500 曲なら 1〜2 リクエスト。10,000 曲でも 10 リクエスト程度。
- 結果は IndexedDB に保存し、次回起動時はキャッシュを即表示してからバックグラウンドで再列挙する。

### 6.3 再生 URL
- 音声要素には Drive のメディア URL を直接渡す：

```
https://www.googleapis.com/drive/v3/files/<fileId>?alt=media&access_token=<token>
```

- iOS のネイティブ音声パイプラインに乗るため、Blob に落とすより再生開始が速く、シークも Range で動く。
- トークンはメモリのみ。URL はメディア要素の src にだけ使い、履歴・共有リンクには残らない。
- トークン残り 5 分を切ったら、曲送り・画面復帰のタイミングで更新する。更新に失敗した場合は現在の曲を止めず、次の操作時に再ログインを促す。

### 6.4 代替（必要になった場合）
- トークンを URL に出したくない、またはオフラインとオンラインを同じ URL で扱いたい場合は、Service Worker で `/media/<fileId>` を横取りし、Authorization 付きで Drive に Range 転送する方式に切り替える。MVP では採用しない。

## 7. ライブラリモデル

実データのタグは不完全（title 45%、album 42%、albumartist 0%、track 番号 2%）。そのため **曲（Track）を主役**にし、アルバムは「本当に複数曲が揃っているときだけ」作る。

```ts
type Track = {
  id: string;            // Drive fileId
  folderId: string;
  fileName: string;      // 元のファイル名（詳細画面で必ず表示）
  title: string;         // タグ or ファイル名から推定
  artist: string;
  album: string;
  albumArtist: string;
  trackNo: number;
  discNo: number;
  year?: number;
  durationSec: number;
  bitrate?: number;
  sizeBytes: number;
  mimeType: string;
  modifiedTime: string;
  hasCover: boolean;
};

type FolderCollection = {
  folderId: string;
  name: string;          // Drive のフォルダ名
  trackIds: string[];
};

type Album = {
  key: string;           // normalize(albumArtist||artist) + "|" + normalize(album)
  title: string;
  artist: string;
  trackIds: string[];    // 2 曲以上のときだけアルバムとして扱う
  coverKey?: string;
};
```

**表示名の決定順**
1. Drive の `audioMediaMetadata`（title / artist / album / trackNumber / year / durationMillis）
2. 無ければファイル名のヒューリスティック
   - `01. Title` / `01 - Title` / `01 Title` → 先頭の番号を除いた部分
   - `A - B` → ライブラリ内の既知のアーティスト名と一致する側をアーティスト、もう一方をタイトルにする。判別できなければ前半をアーティスト、後半をタイトル（170 曲がこの形式）
   - 分割に迷う場合は無理に分けず、ファイル名全体をタイトルとして表示する
   - `[Artist] Title` / `Artist／Title` → 区切りで分割
   - どれにも当たらなければファイル名全体をタイトルにする
3. 元のファイル名は曲詳細に必ず表示し、誤判定をユーザーが確認できるようにする
4. アーティスト不明は「不明なアーティスト」、アルバム不明は「アルバムなし」

**グループ**
- フォルダ：Drive のフォルダをそのままコレクションとして表示（15 個）
- アルバム：同じ album タグの曲が **2 曲以上**ある場合だけ表示。1 曲だけの album タグは無視する（ノイズが多いため）
- アーティスト：タグまたはファイル名から推定。推定できなければ「不明」にまとめる
- 曲順：discNo → trackNo → ファイル名の自然順
- 再列挙で追加・削除・改名を反映する。fileId が変わらないため、プレイリストとキャッシュは維持される

**タグの補完**
- ライブラリ表示には Drive のメタデータとファイル名だけを使う（初回に数百ファイルをダウンロードしない）
- 曲詳細を開いたとき、または「情報を再取得」したときだけ、先頭 256KB を取得して ID3 / MP4 タグを解析する
- 解析結果は IndexedDB に保存し、次回以降は使う

## 8. カバーアート

- サイドカー画像（cover.jpg 等）は 0 枚。埋め込みアートは mp3 の 45% に存在し、m4a には無い。
- したがって**カバーは「あれば嬉しい」扱い**。無い場合は曲名／フォルダ名の頭文字＋グラデーションで表示し、レイアウトが崩れないようにする。
- 第一候補：Drive の `thumbnailLink`。ただし音声では汎用アイコンの可能性が高いので、画像かどうかを確認してから使う。
- 第二候補：曲の先頭 256KB を Range 取得し、ID3v2 の APIC / MP4 の `covr` を解析（`music-metadata-browser`）。曲詳細を開いたとき、またはアルバム表示時だけ、同時 3 件まで。
- 取得したカバーは曲／アルバム単位で IndexedDB に保存し、2 回目以降は通信しない。
- MediaSession の artwork は、カバーがある曲だけ設定する（無ければ省略）。iPhone で Blob が表示されない場合は省略を許容する（Phase 0 で確認）。

## 9. 再生エンジン

**HTMLAudioElement を 1 個だけ**、React ツリーの外で管理する。

- 再生の優先順位：(1) 保存済み Blob（通信ゼロ）→ (2) ストリーミング。毎回の確認ダイアログは出さない。
- ストリーミング時は `audio.src = driveMediaUrl(trackId)`。Drive が Range に対応しているため、シークもそのまま動く。
- 設定「未保存の曲を通信で再生する」（既定 ON）。OFF の場合は保存済みの曲だけ再生し、未保存曲はトーストで案内する。
- オフライン保存済みの曲は IndexedDB の Blob を `URL.createObjectURL` して優先再生する（通信ゼロ、シーク即時）。
- 先読みは「保存済みの次曲」だけ。通信での先読みは許可時のみで、サイズを表示する。
- キュー：配列＋現在位置。シャッフルは再生順を事前生成して保持。リピートは off / all / one。
- 再開：キューの trackIds / index / positionSec を保存し、起動時に「続きから」を出す。
- スリープタイマー：指定分後に停止。`volume` を段階的に下げる（Web Audio は使わない）。
- 再生速度：MVP では等速のみ。
- **Web Audio API は使わない**（iOS のバックグラウンドで AudioContext が suspend されるため）。

## 10. MediaSession / iPhone

- metadata：title / artist / album / artwork
- handlers：play, pause, previoustrack, nexttrack, seekbackward, seekforward, seekto, stop
- `setPositionState` を 1 秒ごとに更新
- `audio` 要素は DOM に常駐。`playsinline` / `webkit-playsinline` を付与
- iOS の制約：
  - 画面ロック中は JS のタイマーや通信が間引かれることがある。音声自体はネイティブが継続するが、**曲の終わりに JS が動かないと自動送りできない**。
  - Phase 0 で「ロック中の自動曲送り」を必須確認する。**事前保存では解決しない**（JS が動かないなら `ended` も動かない）。不可の場合の選択肢は (a) Capacitor でネイティブシェル化（要 Mac / Apple Developer）、(b) ロック画面からの手動送りを許容して Safari タブで使う、のどちらか。曲を 1 ファイルに連結した派生ファイルを作る案は「読み取り専用」の原則に反するため採用しない。
  - マナーモードの影響、Bluetooth 操作は実機で確認する。

## 11. オフライン / データ通信

データを抑えることが主目的なので、**保存済み再生が既定**。ストリーミングは例外扱い。

- 保存単位：曲／アルバム／フォルダ／プレイリスト。まとめて「通学セット」として保存できる。
- 保存はユーザー操作で開始（「Wi-Fi で保存」ボタン）。iOS ではネットワーク種別を自動判別できないため、勝手にダウンロードしない。
- ダウンロードは再開可能。同時 2 件、失敗は指数バックオフ。進捗と合計 MB を表示する。
- 保存済みは常に Blob 再生を優先し、オンラインでも通信しない。
- 再生時のポリシー：
  - 保存済み → そのまま再生
  - 未保存＋モバイル通信 OFF → 再生せず、トーストで「設定で通信再生をONにするか保存」と案内する
  - 未保存＋モバイル通信 ON → そのままストリーミング（確認なし）
- 設定で「未保存の曲を通信で再生する」（既定 ON）、「保存済みのみ表示」（任意）を切り替える。
- 容量：既定 1.5GB、設定で 256MB〜8GB。LRU で削除。`navigator.storage.persist()` を要求する。
- iOS Safari は実質 1GB 前後で、一定期間使わないと eviction されることがある。使用量・残り・保存済み曲数を設定画面に表示する。
- 不足時は「再生中の曲 → キューの次の曲 → 最近聴いた曲」の順で残す。
- オフライン起動：Service Worker がアプリ本体をキャッシュし、カタログと音源が端末にあれば**未ログインでも起動・再生できる**。ログインが必要なのは再列挙・ストリーミング・新規保存のときだけ。
- 通信量の目安を表示：保存済み MB、今月の推定ストリーミング MB（ファイルサイズ×再生回数からの概算）。

## 12. 画面（MVP）

下部タブ：**ホーム / 曲 / ライブラリ / 検索**

- **ホーム**：続きから、通学セット（保存済み X 曲 / 未保存 Y 曲、残り MB、「Wi-Fi で続きを保存」）、最近追加（Drive の modifiedTime）、よく聴く、お気に入り、全曲シャッフル
- **曲**：全曲リスト。行にカバー（あれば）、タイトル、アーティスト、フォルダ名、時間。並べ替えとフィルタ
- **ライブラリ**：フォルダ一覧、アーティスト一覧、アルバム（2 曲以上のものだけ）、プレイリスト、お気に入り、履歴、設定（モバイル通信の許可・容量・使用量）
- **検索**：曲名・アーティスト・フォルダ名・アルバムをローカル即時検索（NFKC + 小文字化）
- **ミニプレイヤー**：タブバー上に常駐。タップで全画面プレイヤー
- **全画面プレイヤー**：カバーまたはプレースホルダ、曲情報（元ファイル名も表示）、シーク、前後、シャッフル、リピート、キュー、スリープタイマー、オフライン保存
- 初回：Google ログイン → フォルダ URL 貼り付け → ライブラリ取得
- カバーが無い曲が多いので、**リスト中心**の落ち着いた見た目にする。VaultStream のダーク基調は踏襲する。

## 13. 設定・保存・デプロイ

- 設定（クライアント ID、フォルダ ID、容量、先読み数、モバイル通信の許可）は localStorage。
- アプリ本体は Service Worker でキャッシュする（VaultStream の `public/sw.js` を流用）。オフライン起動に必須。
- ライブラリ、カバー、音源キャッシュは IndexedDB。
- プレイリスト、お気に入り、履歴、キュー、再生位置は localStorage + IndexedDB。MVP ではクラウド同期しない。
- 第 2 段階で `drive.appdata` スコープを追加し、非表示のアプリデータ領域に JSON を置いて端末間同期する（Drive の UI には出ない）。
- デプロイ：`npm run build` → `npx wrangler pages deploy out --project-name vaultmusic-my`。GitHub Pages でも可。

## 14. フェーズ

- **Phase 0（半日）**：iPhone 実機スパイク。**ここを通るまで UI 実装に入らない（ハードゲート）**。次を確認する。
  1. `alt=media&access_token=` の URL を `<audio>` に入れて再生できるか
  2. 画面ロック後も鳴り続けるか
  3. ロック中に曲が終わったとき自動で次曲へ進めるか（**ストリーミング再生と Blob 再生を別々に**確認）
  4. ロック画面／イヤホンの再生・停止・次へ・前へが効くか
  5. MediaSession の artwork が表示されるか
  6. トークンが切れる 60 分後も、ロックしたまま次の曲へ進めるか
  7. 機内モードで保存済み Blob が鳴るか
  8. ログイン後にオフラインで起動し、保存済みの曲を再生できるか
  不可なら設計を見直す（Capacitor は要 Mac / Apple Developer。Safari タブでの手動送り許容も選択肢）。
- **Phase 1（コア）**：ログイン、フォルダ指定、列挙、アルバム一覧、再生／一時停止、キュー、シーク。
- **Phase 2（通学仕様）**：バックグラウンド、ロック画面、オフライン優先（通学セット・保存済み再生・未保存時の確認）、続きから、スリープタイマー、トークン更新。
- **Phase 3（整理）**：検索、プレイリスト、お気に入り、履歴、設定、カバー遅延取得の仕上げ。
- **Phase 4（任意）**：appdata 同期、Service Worker 経由の `/media/` 配信、複数フォルダ対応。

MVP = Phase 1 + 2。

## 15. 受け入れ基準

1. 約 500 曲のライブラリが、キャッシュありで 2 秒以内、初回でも 5 秒以内に表示される。
2. iPhone で画面ロック後 30 分以上、10 曲以上が**自動で曲送りされながら**再生される。
3. ロック画面／イヤホンの再生・停止・次へ・前へが効く。
4. オフライン保存したアルバムが機内モードで再生できる。
5. モバイル通信 OFF のとき、未保存の曲は勝手に通信せず、案内が出る。
6. 保存済みの曲だけで 1 時間再生したときの通信量が 0MB である。
7. オフラインかつ未ログインで冷起動し、保存済みの曲を再生できる。
8. アプリを完全終了して再起動すると、同じ曲の同じ位置から再開できる。
9. オンラインで曲をタップしてから 2 秒以内に音が出る（通信許可時）。
10. 再生できない形式（opus 等）は一覧で判別できる、または明示的に除外される。
11. タグの無い曲も、ファイル名から判別できる表示名で一覧に出る。元ファイル名は詳細で確認できる。
12. Drive 上のファイルを作成・変更・削除しない（読み取りのみ）。
13. `pwa` の `npm run build` が成功し、既存 VaultStream に影響がない。

## 16. リスクと対策

| リスク | 対策 |
| :--- | :--- |
| iOS PWA のバックグラウンド音声／自動送りが不安定 | Phase 0 をハードゲートにして実機判定。不可なら Capacitor（要 Mac / Apple Developer）か Safari タブでの手動送り。事前保存では自動送りは直らない |
| トークンが 1 時間で切れる | 残り 5 分で更新。失敗時は現在の曲を止めず、次の操作で再ログインを促す |
| `audioMediaMetadata` が空（Drive 未解析） | ID3 / MP4 タグのクライアント解析で補完。ファイル名フォールバック |
| タグが不完全で曲名が崩れる | Drive メタデータ → ファイル名推定の順で補完。元ファイル名を詳細に併記し、曲詳細でタグを再解析 |
| カバー取得で通信量が増える | `thumbnailLink` 優先、見えているアルバムのみ、IndexedDB キャッシュ |
| opus が iOS で再生できない | 一覧で警告、MVP では再生対象外 |
| iOS のストレージ上限が小さい | 既定 1.5GB、使用量表示、LRU、通学セットを小さく保つ |
| モバイル通信を自動判別できない | 明示スイッチ（既定 OFF）＋保存済みバッジ。未保存曲はサイズ確認を挟む |
| 未保存曲ばかりで通信が増える | ホームに「通学セットの残り」を出し、Wi-Fi 保存を促す。再生前にサイズを表示 |
| Drive API のレート制限・遅延 | 列挙は 1000 件単位、キャッシュ即表示、カバーは低並列 |
| フォルダ内の曲構成が変わる | 起動時と手動更新で再列挙。fileId 基準なのでプレイリストは維持 |
| トークンが URL に載る | メディア要素の src のみ。履歴・共有・referrer に残らない。気になる場合は SW 配信に切り替え |

## 17. プライバシー

- 音源は暗号化しない。Drive 上では今までどおりファイル名・タグが見える（方式 C の前提）。
- アプリは指定フォルダの **読み取りのみ**。作成・更新・削除・共有はしない。
- アクセストークンはメモリのみ。リフレッシュトークンは保持しない。
- 解析・トラッキング・外部送信はしない。
- プレイリスト等のユーザーデータは端末内のみ（Phase 4 で Drive の appdata 領域に同期する場合も非公開領域）。

## 18. 未決事項

- 主端末は **iPhone**（決定）。
- データ通信は抑えたい（決定）。モバイル通信は既定 OFF、保存済み再生を優先する。
- オンラインで新規取得するときだけ Google ログインを求める。オフライン再生はログイン不要にする。
- 低ビットレート版が必要になった場合は、読み取り専用の原則を崩して別フォルダに派生ファイルを作る案を再検討する（MVP 外）。
- Phase 0 でバックグラウンド再生が不安定だった場合の代替（Capacitor / Safari タブ）は検証結果で決める。
- opus の 1 曲を除外するか、警告付きで表示するか（Phase 1 で実機確認して決める）。
- appdata 同期を MVP に含めるか（現状は Phase 4）。
